# Agent Note: Desktop configuration schemes and verified GitHub Release updates

Status: implemented

English | [中文](2026-08-16-desktop-configuration-schemes-and-release-updates.zh.md)

## Problem

The first DeepSeeker desktop release reused one Web profile and shipped no Windows installer or update path. A regular user could not keep work and personal credentials, models, plugins, and sessions apart without manually changing Harness files. Published fixes also required finding and replacing the application by hand. A profile switch or failed update must not stop a healthy running Host.

## Decision

The Electron shell owns user-facing configuration schemes outside the model-visible Harness tree. The built-in Default scheme reuses the ordinary Harness home. Each created scheme receives an opaque UUID directory and a separate Harness home under Electron user data; its editable label never becomes a filesystem segment. Per-scheme metadata and the selection state use private directories, private files, bounded reads, and atomic replacement. Metadata allows names to be recovered when the central state file is malformed.

Selection is restart-based. Before persisting a target, Electron runs the packaged or source CLI as `dsh --profile web --dump-config` with the candidate `DSH_HOME` in a separate process. The check has a 30-second bound and bounded diagnostics. Failure leaves the current Host and renderer running. Success records a pending target, requests Electron relaunch, and enters the existing graceful Host shutdown. Startup consumes the pending target but retains last-known-good until the selected Host reaches readiness and the main renderer loads. If the process exits during that interval, the next launch detects the unconfirmed active selection, persists a rollback, and boots last-known-good. A reported startup failure waits for the rejected Host process to exit before restoring and booting last-known-good. Every Host supervisor is registered before its readiness wait. Application quit cancels and joins an active profile check, stops fallback startup, joins a pending terminal open, and then releases the application only after the owned Host and PTY have stopped.

The configuration manager is a separate sandboxed BrowserWindow containing a static data document. It has no preload, Node integration, or inline script. Forms navigate only to an allowlisted inert HTTPS origin; the main process parses those attempted navigations into create, rename, select, delete, and close commands. Deleting requires a native warning whose safe default is Cancel. The built-in, running, last-known-good, and pending schemes are protected. An eligible scheme directory is first moved to a private tombstone, then removed with its complete Harness home after the state update succeeds. Symbolic-link replacement is rejected. The manager is modal only while the main window is visible; a tray request made while the main window is hidden opens an independent window. The tray exposes the current scheme and the manager. The product copy calls the feature “Configuration schemes” rather than Profile.

The tray also exposes an advanced local desktop terminal. A sandboxed renderer and narrow preload host xterm, while the main process lazily loads `node-pty`, validates renderer ownership, bounds input and dimensions, and owns one PTY at a time. Shell resolution covers PowerShell 7, Windows PowerShell, `cmd.exe`, and POSIX shells. The environment removes inherited credentials and all inherited `DSH_*` values, then adds only the active scheme's `DSH_HOME` and the desktop marker. Close requests escalate from graceful termination to forced process-tree cleanup, and application exit keeps a synchronous force-stop fallback. Each synchronous Windows `taskkill.exe` invocation has a five-second deadline and is killed if the helper stalls. The native PTY is explicitly unpacked from ASAR and its preload is built as a separate CommonJS artifact.

Packaged macOS and Windows applications check `deepseeker-app/DeepSeeker` through the public GitHub Releases API after 60 seconds and every six hours. Automatic checks only update the tray and notify once per process. Manual checks ask before downloading. Asset discovery accepts stable releases and platform/architecture-compatible `.dmg`, `.zip`, or `.exe` assets whose page and download URLs belong to this repository.

Confirmed downloads go to a private version directory below Electron user data. Release discovery has a 15-second total deadline. Installer downloads use a 30-second no-progress watchdog that is armed only while waiting for the response or next body chunk, so a progressing large download has no fixed total limit. The downloader also limits API and artifact sizes, bounds asset names, restricts final redirects to GitHub-owned HTTPS hosts, streams without buffering the installer, reports progress, and atomically publishes only after exact Release size, required GitHub SHA-256, and container signature validation. A completed installer is reused only after the same validation; an invalid old file remains in place until a verified replacement is ready. A timeout cancels the request and removes its partial file. An asset without a GitHub digest remains reachable from its Release page but is not offered for in-app download. macOS opens a verified DMG or ZIP without exiting. Windows asks again, starts the verified installer without a shell, and quits only after the child emits `spawn`. Every failure retains the current application.

The desktop package version is `0.2.0`. Host staging uses pnpm's legacy deploy, which temporarily rewrites the source workspace dependency layout; the staging script relinks the workspace from the frozen lockfile after success or failure, so the source CLI remains runnable after packaging. The macOS packaging command removes the stable-name archive and sidecar before invoking Electron Builder, replaces incomplete inherited linker signatures with one recursive ad-hoc signature, rejects the bundle unless strict deep verification passes, and then streams the new archive digest into `DeepSeeker-mac-arm64.zip.sha256` without buffering the archive in memory. This proves bundle integrity but provides neither a Developer ID identity nor Apple notarization. The after-pack check requires the Host entrypoints, main process, terminal preload, xterm CSS, native PTY binary, and macOS spawn helper. Windows Electron Builder output is a per-user x64 NSIS installer named `DeepSeeker-windows-x64-setup.exe`. The tag-driven Windows workflow requires the tag to equal `v<desktop version>`, builds on `windows-latest`, checks the PE header, silently installs into a temporary directory, starts the installed Electron runtime in Node mode, checks the Host and native PTY files, silently uninstalls, emits its SHA-256 sidecar, and uploads both Windows files to a draft GitHub Release using repository `contents: write` permission. The draft is published only after the macOS archive and both platform checksum files are present. The Pages workflow refuses deployment unless the public latest Release matches the desktop version, contains all four assets, and each downloaded sidecar names the expected artifact and agrees with its GitHub SHA-256 digest.

## Verification

The desktop tests cover scheme name validation, private and isolated storage, create, rename, protected deletion, private-home deletion, symbolic-link rejection, pending selection, last-known-good promotion, reported-failure rollback, interrupted-launch recovery, shutdown cancellation, corrupted-state recovery, and cleanup of a rejected new scheme. Manager tests pin escaping, no-script CSP, the exact action origin, and the delete command. Host tests cover successful, failed, timed-out, and application-cancelled profile probes, including joined child exit. Terminal tests cover shell selection, environment filtering, path validation, bounded input and dimensions, Windows helper deadlines, process-tree termination, renderer/preload wiring, and no-script CSP. Update tests cover SemVer ordering, macOS and Windows asset selection, no-update versus failed checks, stalled discovery and download timeouts, verified installer reuse and replacement, progress, exact size and digest validation, ZIP signature validation, redirect rejection, and partial-file cleanup. Integration source checks pin validation-before-persist, early Host ownership, failed-Host cleanup before fallback, readiness-before-promotion, hidden-window manager behavior, confirmation-before-delete, confirmation-before-download, confirmation-before Windows execution, `DSH_HOME` isolation, pending-terminal cleanup, and sandboxed windows. Packaging tests pin version `0.2.0`, NSIS settings, native PTY unpacking, packed terminal resources, ad-hoc signing and strict verification before macOS compression, deletion of stale stable-name macOS artifacts before a build, automatic macOS sidecar generation, Windows silent install/runtime/uninstall smoke coverage, draft Windows Releases, and Pages reconciliation of the release assets and checksums. Release acceptance extracts the final ZIP and repeats strict signature verification, version inspection, runtime entry checks, archive integrity, and SHA-256 validation.

## Alternatives considered

**Use upstream Harness profiles under one Harness home.** Those profiles isolate composition patches and plugins, but base settings and credentials still live at the Harness-home level. Separate homes match the user-facing promise that work and personal schemes do not share keys, models, or sessions.

**Stop the current Host and test a selection in place.** A bad profile would turn a reversible selection into an outage. The detached dump-config probe verifies composition before any healthy process is touched, while startup rollback covers failures that only appear during full boot.

**Use Electron autoUpdater or download unvalidated browser URLs.** Generic autoUpdater assumes a provider-specific feed and platform artifact contract. Direct GitHub discovery keeps Releases as the single storage service, while explicit URL, size, digest, and file-format checks make the manual installation handoff bounded.

**Open the system terminal with a shell shortcut.** That path cannot reliably connect input, output, resize, process ownership, the active scheme environment, and application shutdown. An application-owned PTY keeps those boundaries testable and makes cleanup explicit.

## Consequences

Users can create, rename, switch, and delete clearly named, genuinely isolated working environments without editing files. The currently healthy Host survives every preflight failure, and last-known-good state contains a boot-time failure. Advanced users can open a local terminal bound to the active scheme without giving renderer code direct process access. GitHub Releases provide both discovery and artifact storage, and the stable Windows filename supports an unversioned `/releases/latest/download/` website link.

Switching intentionally restarts the desktop application. Deleting a scheme permanently removes its private settings, credentials, plugins, and sessions after confirmation. Automatic checks need outbound access to `api.github.com`, and downloads need GitHub Release hosts. The macOS ZIP is ad-hoc signed but not Developer ID-signed or Apple-notarized, so a downloaded copy can require Control-click Open or quarantine removal after digest verification. The Windows installer is not Authenticode-signed yet; the workflow needs no extra secret until signing is added. Linux still has no installer or automatic update handoff. The desktop terminal is local, single-session, and still needs final interactive ConPTY acceptance on Windows.
